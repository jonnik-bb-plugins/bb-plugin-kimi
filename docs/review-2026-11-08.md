# Review: bb-plugin-kimi 0.1.0

- Date: 2026-11-08
- Reviewed commit: `855867e` (feat: Kimi Code CLI as bb ACP provider)
- Environment: bb 0.49.0, Kimi Code CLI 2.5.2, macOS

## Verdict

The code is tidy and builds, but `v0.1.0` is not ready to tag. Two of bb's
three permission modes do not behave as the README states, and release
prerequisites are missing (`dist/` not committed, `OWNER` placeholders, no
remote, no tag).

## What was checked

- `npm run typecheck` — passes.
- `npm test` — 13/13 pass.
- `bb plugin build .` on a clean `git archive HEAD` copy — passes;
  `dist/*.meta.json` has `pluginId: kimi`, `pluginVersion: 0.1.0`.
- Kimi CLI flag parsing (`kimi --help`, `kimi acp --help`, direct invocation)
  and a live ACP `initialize` + `session/new` handshake under each flag.
- How bb composes the launch command, from the bundled `provider-acp`
  (`applyPermissionCliArgs` in `dist/host.js`).

Not checked: a live install in bb (`bb plugin install .`, `bb kimi status`,
`bb provider models acp-kimi`) — it mutates bb settings and was not run.

## Critical

### 1. `permissionCli` has no effect; the README permission table is wrong

Files: `src/agent-entry.ts:28-31`, `README.md:66-79`,
`config/custom-acp-agent.json:11-14`.

- bb inserts permission flags **before** `args` (`insertAfterArgs` defaults to
  0), so the launch command is `kimi --yolo acp`. That form starts; `kimi acp
  --yolo` would fail with `unknown option '--yolo'`.
- Kimi's ACP server ignores the root flags. With no flag, `--yolo` and `--auto`
  alike, `session/new` returns `modes.currentModeId: "default"` ("Manual
  approvals").
- Actual behaviour:
  - **Accept edits** behaves like Auto: Kimi asks for every tool call. bb only
    adds its own deny for `fs/write_text_file` outside the workspace roots.
  - **Full access** works, but because bb itself answers every
    `session/request_permission` with `allow_once` in `full` mode, not because
    of `--auto`.
  - Since the flags differ per mode, changing a thread's permission mode also
    restarts the agent process for no effect.
- Naming is inverted between surfaces: CLI `--yolo` = Ask When Needed, `--auto`
  = Never Ask; ACP modes `auto` = "Auto-approve safe operations", `yolo` =
  "Auto-approve everything".

Recommendation: drop `permissionCli`, rewrite the README table to describe the
real behaviour, and mention that Kimi's mode is selectable through the `mode`
session config option it advertises over ACP. File an upstream Kimi issue for
`kimi acp` to honour `--yolo`/`--auto` (if it lands as an `acp` subcommand
option, use `insertAfterArgs: 1`).

### 2. Release prerequisites missing

- `dist/` is not committed (only an empty leftover `dist/.stage-CMgwLq` from an
  interrupted build). Git-sourced marketplace installs and the
  `git diff --exit-code dist` step in `AGENTS.md` will fail.
- `OWNER` placeholders in `package.json:15-21` and `README.md:28`.
- Commit author is `bb-plugin-kimi <dev@localhost>`; the marketplace PR must
  come from `author.github`.
- No git remote and no `v0.1.0` tag.

## Major

### 3. The recorded `kimi` path is never reused

File: `server.ts:44`.

`existing.command.includes(delimiter)` uses `path.delimiter` — the PATH list
separator (`":"` on POSIX) — so it is always false for an absolute path
(verified: `"/Users/x/.kimi-code/bin/kimi".includes(":") === false`).

Impact: every boot replaces `command` with the first `kimi` found by search. A
user-pinned wrapper is lost, and the legacy Python `kimi-cli` in
`~/.local/bin` (same binary name) can be picked instead.

Fix: use `isAbsolute(existing.command)`.

### 4. A malformed `customAgents` setting silently falls back to legacy `config.json`

Files: `server.ts:117-138`, `server.ts:161-174`.

`parseCustomAgents` throws on invalid JSON or a non-array; `readSettingAgents`
catches it and returns `null`; after 10 retries `provision` writes
`customAcpAgents` into `<dataDir>/config.json` and calls `reloadConfig()`. That
array was removed in bb 0.41 (current bb is 0.49), so the provider is not
registered, yet the boot log says `registered acp-kimi`. The same path is taken
if the startup 404 race lasts longer than ~5 s.

Fix: distinguish a parse error (report via `bb.status.needsConfiguration`
immediately, do not retry) from a transient unavailability; drop the legacy
write path for current bb versions.

### 5. Unguarded read-modify-write of the shared `customAgents` setting

`customAgents` is one string shared by every ACP provider plugin (auggie,
etc.), and each rewrites it whole at boot. Concurrent provisioning can lose
another plugin's entry. This is inferred from the API shape, not reproduced.
At minimum, re-read after writing and verify the entry is present.

## Minor

- **6.** `bb kimi repair` does not clear a boot-time `needs-configuration`
  status — per the SDK it clears only on the next load. Print a
  `bb plugin reload kimi` hint on successful repair.
- **7.** `status` (`server.ts:246-268`) reports `missing` when the settings
  read failed, swallows `providers.list()` errors in `catch {}`, and throws
  unhandled on a malformed `config.json`.
- **8.** `config/custom-acp-agent.json` is unused and duplicates `PROFILE`; it
  will drift. Delete it or generate it.
- **9.** `zod` is listed in `dependencies` but not imported.
- **10.** `engines.bbPluginSdk: ">=0.4.8"` is unverified: the build uses SDK
  0.6.132 and relies on `experimental_providerIcon` and `plugins.getSettings`.
- **11.** Tests cover only the pure helpers in `src/agent-entry.ts`. Binary
  lookup, retries, the legacy fallback and migration in `server.ts` are
  untested; findings 3 and 4 would have been caught. `bb-plugin-sdk-testing`
  from the SDK can host these tests.
- **12.** README model examples (`kimi-code/k3`, …) are stale; Kimi now
  defaults to `kimi-code/k3.1-pro`. The catalog itself is dynamic, so this is
  docs only.

## Strengths

- Atomic writes with `0600` permissions.
- Refuses to overwrite a setting that is not a JSON array.
- Preserves user-added keys on the managed entry; upsert is idempotent.
- Leaves other agents untouched.
- Theme-following `currentColor` icon.
- No hard-coded model catalog or auth methods.
- ACP capabilities claimed in the README (`loadSession`, image prompts,
  resume/fork, `login` auth) match Kimi's `initialize` response.
